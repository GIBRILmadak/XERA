L'API XERA1 est une API REST qui alimente les interactions principales de la plateforme. Vous pouvez l'utiliser pour suivre l'engagement des utilisateurs, récupérer les données du fil classé algorithmiquement, mettre à jour les métriques de contenu et gérer chaque aspect de la monétisation des créateurs : du résumé du portefeuille aux retraits Mobile Money. Toutes les requêtes sont envoyées à une seule URL de base, toutes les réponses sont en JSON et tous les endpoints protégés nécessitent un jeton de session valide.

## URL de base

Chaque requête API cible l'URL de base suivante en production :

```text
https://xera1.xyz
```

Préfixez tous les chemins d'endpoint avec cette URL. Par exemple, l'endpoint de fil de découverte est accessible à `https://xera1.xyz/api/app/discover/users`.

<Note>
  Il n'y a pas de segment de version dans le chemin. Les endpoints de la plateforme authentifiés se trouvent sous `/api/app/*`. Les endpoints de revenus créateurs et de monétisation se trouvent sous `/api/creator-revenue/*` et `/api/monetization/*`.
</Note>

## Format de réponse

Chaque réponse de l'API XERA1 est un objet JSON. Les réponses réussies incluent un indicateur `success: true` accompagné d'une charge utile `data` :

```json
{
  "success": true,
  "data": {
    "id": "a1b2c3d4-...",
    "interaction_type": "like",
    "created_at": "2025-01-15T10:30:00.000Z"
  }
}
```

Les réponses d'erreur incluent toujours une chaîne `error` décrivant ce qui s'est mal passé. L'indicateur `success` est soit `false`, soit absent :

```json
{
  "success": false,
  "error": "Missing required field: target_user_id"
}
```

Certains endpoints retournent un objet d'erreur plat sans la clé `success` :

```json
{
  "error": "Missing required field: target_user_id"
}
```

Votre code client doit vérifier la présence d'un champ `error` ou une valeur `success: false` avant de traiter le corps de la réponse.

## Codes HTTP

XERA1 utilise les codes HTTP standards pour signaler le résultat de chaque requête.

| Code | Signification | Quand vous le verrez |
| --- | --- | --- |
| `200 OK` | Requête réussie | GET ou POST réussi qui retourne des données |
| `201 Created` | Ressource créée | Insertion de ressource réussie (certains endpoints) |
| `400 Bad Request` | Entrée invalide ou manquante | Champs requis manquants dans le corps de la requête |
| `401 Unauthorized` | Échec d'authentification | Jeton manquant, expiré ou invalide |
| `403 Forbidden` | Permissions insuffisantes | Authentifié mais non autorisé pour la ressource |
| `404 Not Found` | La ressource n'existe pas | Utilisateur, contenu ou enregistrement non trouvé |
| `500 Internal Server Error` | Échec côté serveur | Erreur inattendue : réessayez ou contactez le support |

## Patterns d'erreur courants

Les champs requis manquants retournent un `400` avec un message descriptif :

```json
{
  "success": false,
  "error": "interaction_type et target_user_id sont requis"
}
```

Un jeton expiré ou manquant retourne `401` :

```json
{
  "success": false,
  "error": "Utilisateur non authentifié."
}
```

Un échec serveur inattendu retourne `500` :

```json
{
  "success": false,
  "error": "Erreur serveur"
}
```

<Tip>
  XERA1 retourne les messages d'erreur en anglais ou en français selon l'endpoint. Votre intégration doit gérer les deux et afficher un message convivial plutôt que d'exposer les erreurs brutes de l'API.
</Tip>

## Limitation de débit

Les endpoints XERA1 sont limités en débit pour protéger la santé de la plateforme et garantir un accès équitable pour tous les builders. Si votre intégration envoie trop de requêtes dans une courte fenêtre, vous pouvez recevoir une réponse `429 Too Many Requests`. Implémentez une stratégie de backoff exponentiel et évitez de poller les endpoints en boucles rapides : utilisez les données retournées par chaque appel pour déclencher les requêtes suivantes uniquement lorsque nécessaire.
